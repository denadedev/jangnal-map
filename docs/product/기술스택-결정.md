## 2. 최종 시스템 구조

```text
사용자 브라우저
  ├─ 웹 요청 ───────────────→ Vercel
  │                           └─ Next.js 프론트엔드
  │
  └─ API 요청 ──────────────→ api.<domain>:443
                              └─ NPM Plus (TLS 종료·프록시)
                                  └─ K3s Service
                                      └─ NestJS REST API
                                          ├─ TypeORM
                                          │   └─ PostgreSQL + PostGIS
                                          └─ JSON 로그
                                              └─ Loki → Grafana

GitHub
  └─ GitHub Actions
      ├─ 검사·테스트
      ├─ 백엔드 이미지 → Harbor:<commit-sha>
      └─ 배포 매니페스트 이미지 태그 갱신
          └─ Argo CD → K3s 동기화
```

## 3. 저장소와 애플리케이션 경계

프론트엔드와 백엔드는 한 저장소에서 관리하지만 별도 애플리케이션과 배포 단위를 유지한다.

```text
apps/
├── web/                 # Next.js, Vercel 배포
└── api/                 # NestJS, K3s 배포
packages/
└── contracts/           # 공개 API 계약에서 생성·공유할 타입
deploy/                  # Argo CD가 읽는 K3s 배포 선언
```

세부 디렉터리명은 구현 계획에서 기존 도구의 권장 구조와 충돌 여부를 확인한 뒤 확정한다. 저장소 경계의 원칙은 다음과 같다.

- 프론트엔드는 TypeORM Entity나 데이터베이스 모듈을 import하지 않는다.
- 백엔드의 도메인·애플리케이션 로직은 NestJS Controller에서 분리한다.
- Controller는 요청 검증, 유스케이스 호출과 응답 변환만 담당한다.
- TypeORM은 인프라 계층에 두고 PostGIS 쿼리를 전용 Repository에 격리한다.
- 관리 CLI는 HTTP를 우회해 데이터를 직접 수정하지 않고 백엔드의 동일한 애플리케이션 유스케이스를 호출한다.
- API 경로는 `/api/v1`부터 시작해 프론트엔드와 백엔드 배포 주기를 분리한다.

## 4. 프론트엔드

### 4.1 선택

- Next.js와 TypeScript
- Tailwind CSS와 shadcn/ui
- TanStack Query
- 날짜, 지역과 검색 조건은 URL 검색 파라미터로 보존
- 별도 전역 상태 라이브러리는 MVP에 추가하지 않음

### 4.2 배포

- 프론트엔드는 Vercel Hobby에 배포한다.
- Vercel은 프론트엔드만 담당하며 개인 서버 PostgreSQL에 직접 연결하지 않는다.
- 서비스가 광고, 결제 또는 다른 상업적 이용을 시작하기 전에 Vercel Pro 전환을 검토한다.
- 운영 도메인과 Preview 도메인별 API 허용 출처 정책을 분리한다.

## 5. 백엔드와 API

### 5.1 선택

- NestJS와 TypeScript
- REST API
- TypeORM
- OpenAPI를 API 계약의 기준으로 사용

### 5.2 경계

- 공개 읽기 API: 지도 영역 시장, 날짜 필터, 시장 검색, 시장 상세
- 공개 쓰기 API: 비로그인 오류 제보
- 내부 운영 기능: SSH 기반 관리 CLI
- 관리자 웹 API와 OAuth 로그인은 MVP에서 제공하지 않는다.

### 5.3 보안 기본값

- 운영 CORS 허용 출처를 Vercel 운영 도메인으로 제한한다.
- NPM Plus가 전달한 클라이언트 IP를 신뢰할 프록시 범위 안에서만 사용한다.
- 제보 API에는 요청 제한과 honeypot 검사를 적용한다.
- 데이터베이스 자격증명과 Harbor 자격증명은 코드 또는 이미지에 포함하지 않는다.
- PostgreSQL 포트는 인터넷에 공개하지 않는다.

## 6. 데이터베이스와 장날 계산

### 6.1 데이터베이스

- 개인 서버에서 이미 운영 중인 PostgreSQL을 사용한다.
- PostGIS 확장을 사용해 지도 영역, 거리순과 좌표 유효성 관련 쿼리를 처리한다.
- TypeORM `synchronize` 기능은 운영에서 사용하지 않고 버전 관리되는 migration만 적용한다.
- K3s 백엔드는 개인 서버 내부 네트워크를 통해 데이터베이스에 연결한다.

### 6.2 장날 계산

정규화된 장날 규칙을 원본으로 유지하면서 향후 12개월의 실제 장날을 파생 테이블에 생성한다.

```text
원본 개설주기
  → 검증·정규화 규칙
  → 향후 12개월 장날 생성
  → 지도 날짜 필터·다음 장날 조회
```

- 최초 적재 시 공개 가능한 시장의 발생일을 생성한다.
- 운영자가 장날 규칙을 수정하면 해당 시장의 발생일만 다시 생성한다.
- K3s CronJob이 월 1회 계산 범위를 연장한다.
- 발생일은 파생 데이터이므로 정규화 규칙에서 재생성할 수 있어야 한다.
- 날짜 조건과 위치 조건에 필요한 B-tree 및 PostGIS 공간 인덱스를 둔다.

## 7. 지도

- NAVER Maps Web Dynamic Map API를 사용한다.
- 시장명과 다음 장날은 사용자 정의 오버레이로 표시한다.
- 핀이 겹치는 축척에서는 클러스터를 사용하고 개별 표시 단계에서는 시장명과 날짜를 유지한다.
- 시장과 장날 검색 결과는 자체 REST API가 제공하며 지도 제공업체의 장소 검색을 서비스 데이터 원본으로 사용하지 않는다.
- 외부 길찾기 연결 방식은 지도 연동 설계에서 NAVER 지도 공식 연결 규격을 확인해 확정한다.

## 8. 테스트

- Vitest: 장날 파서·계산기, 도메인 서비스, API 유스케이스와 프론트엔드 단위 테스트
- Testcontainers: 실제 PostgreSQL/PostGIS 기반 Repository와 migration 통합 테스트
- Playwright: 지도 탐색, 핀 선택, 다음 장날 확인과 오류 제보 흐름
- 장날 계산은 월말, 윤년, 연말·연초와 미확정 규칙을 포함한다.
- 지도 SDK는 경계 어댑터를 모킹하되, 공개 전 실제 NAVER 지도 기반 브라우저 흐름을 별도로 검증한다.

## 9. 배포와 운영

### 9.1 프론트엔드

- GitHub 저장소와 연결된 Vercel Hobby가 `apps/web`을 배포한다.
- 운영 브랜치와 Preview 배포 정책은 구현 계획에서 확정한다.

### 9.2 백엔드

```text
GitHub Actions
  → 검사·테스트 통과
  → Harbor에 <commit-sha> 이미지 push
  → Git의 배포 매니페스트 태그 갱신
  → Argo CD가 변경 감지
  → K3s rollout
```

- `latest`와 같은 가변 이미지 태그를 사용하지 않는다.
- Harbor Robot Account를 사용하고 자격증명은 GitHub Actions Secrets에 보관한다.
- NPM Plus가 운영 API 도메인의 TLS 인증서와 외부 프록시를 담당한다.
- NPM Plus에서 K3s 서비스로 전달하는 내부 주소·포트는 실제 클러스터 확인 후 확정한다.
- readiness와 liveness probe가 통과한 인스턴스에만 요청을 보낸다.

### 9.3 관측

- NestJS는 요청 식별자, 경로, 상태, 처리시간과 오류를 구조화 JSON으로 표준 출력에 기록한다.
- 기존 로그 수집 경로를 통해 Loki에 저장하고 Grafana에서 조회한다.
- API 오류율, 제보 실패, 응답시간과 배포 직후 오류를 확인할 대시보드를 둔다.
- MVP에는 Sentry, Redis 또는 별도 관리형 관측 서비스를 추가하지 않는다.

## 10. 운영자 도구

MVP에는 관리자 웹페이지와 외부 OAuth 인증을 만들지 않는다. 운영자는 개인 서버에 SSH로 접속해 관리 CLI를 실행한다.

관리 CLI의 최소 기능은 다음과 같다.

- 대기 중인 제보 목록과 상세 조회
- 제보 승인·반려와 처리 메모 기록
- 시장·장날 정보 수정
- 시장 상태를 `운영` 또는 `폐장`으로 변경
- 변경 이력 조회와 복구

모든 변경 명령은 애플리케이션 유스케이스, 입력 검증과 트랜잭션을 거쳐야 한다. 직접 SQL 수정은 비상 복구 외에는 운영 절차로 사용하지 않는다.

관리자 웹페이지 도입 조건은 다음 중 하나로 한다.

- 제보가 주 5건을 지속적으로 초과
- 미처리 제보가 20건 이상 누적
- 두 번째 운영자가 추가

## 11. 캐시와 초기 확장 기준

- MVP에는 Redis를 사용하지 않는다.
- 지도 영역·발생일 조회는 데이터베이스 인덱스로 처리한다.
- 공개 읽기 응답에는 데이터 변경 특성에 맞는 HTTP 캐시 헤더와 검증자를 사용한다.
- 캐시 무효화는 시장 또는 장날 수정 시점에 명시적으로 처리한다.
- 실제 데이터와 부하 시험에서 목표 응답시간을 충족하지 못할 때만 Redis 또는 별도 캐시를 검토한다.

## 12. 구현 전 확인 사항

다음 항목은 제품·기술 선택이 아니라 실제 환경 확인 사항이다.

- PostgreSQL 버전과 PostGIS 설치·활성화 권한
- K3s 버전과 NPM Plus에서 접근 가능한 서비스 주소·포트
- Argo CD가 감시할 저장소·경로와 자동 동기화 정책
- Harbor 프로젝트, Robot Account와 인증서 신뢰 상태
- GitHub 저장소 공개 범위와 Actions에서 Harbor 접근 가능 여부
- 운영·Preview 도메인과 CORS 허용 출처
- 기존 Loki 수집기와 Grafana 데이터 소스 구성
- PostgreSQL 백업 주기, 보관 위치와 복구 시험 결과

## 13. 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 개인 서버 또는 회선 장애 | Vercel 화면은 열리지만 시장 데이터 조회 실패 | 복구 가능한 오류 화면, API 상태 확인, 백업·복구 절차 |
| Vercel과 개인 서버 간 교차 출처 설정 오류 | 지도 데이터 요청 차단 | 운영·Preview 출처를 명시적으로 허용하고 브라우저 테스트 |
| NPM Plus가 잘못된 클라이언트 IP 전달 | 모든 사용자가 같은 제한을 받거나 제한 우회 | 신뢰 프록시 범위와 전달 헤더 통합 테스트 |
| PostGIS 미설치 또는 버전 불일치 | 공간 쿼리와 migration 실패 | 구현 전 확장 확인, Testcontainers와 운영 전 migration 검증 |
| Harbor 또는 Argo CD 인증 실패 | 새 백엔드 배포 중단 | Robot Account 최소 권한, 이미지 pull 사전 검증, 이전 태그 유지 |
| 12개월 발생일 연장 실패 | 먼 미래 날짜 검색 누락 | CronJob 상태 관측, 남은 계산 기간 경고, 재실행 가능한 생성 명령 |
| Vercel Hobby 이용조건 변경 또는 상업화 | 배포 중단 또는 약관 위반 | 사용량·약관 정기 확인, 상업화 전 Pro 전환 |
