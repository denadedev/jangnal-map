# 오늘장날 제품 요구사항 문서(PRD)

- 문서 상태: APPROVED
- 작성일: 2026-08-30
- 제품명: 오늘장날(가칭)
- 대상 릴리스: MVP
- 문서 버전: 1.1
- 기준 문서: `서비스-설계.md`, `데이터조사-계획.md`

> 이 문서는 제품 범위와 성공 조건을 정의한다. 사용자 승인 전에는 기술 스택을 확정하거나 애플리케이션, 패키지, 프로젝트 구조, 데이터베이스, 지도 연동을 구현하지 않는다.

## 1. 제품 요약

오늘장날은 전국 지도에서 전통시장의 위치, 시장명, 다음 장날을 한눈에 보여주고, 시장을 선택하면 방문에 필요한 상세정보를 확인할 수 있는 반응형 웹서비스다.

## 2. 문제

전통시장 장날 정보는 공공데이터, 지자체 관광 페이지, 시장 홈페이지와 블로그 등에 흩어져 있다. 같은 시장도 출처마다 표기와 기준일이 다르고, `1·6일장`, `2·7일장`, 요일 기반 장날처럼 규칙이 다양하다. 휴장, 이전, 폐장 같은 예외도 있어 검색 결과 하나만으로 방문일을 정하기 어렵다.

현재 사용자는 다음 문제를 겪는다.

- 가고 싶은 시장의 다음 장날을 찾기 위해 여러 출처를 비교해야 한다.
- 시장 목록만으로는 주변 시장의 위치와 장날을 함께 비교하기 어렵다.
- 정보가 언제, 어디에서 확인됐는지 알기 어려워 신뢰도를 판단할 수 없다.
- 잘못된 정보를 발견해도 제보하거나 정정 결과를 확인할 일관된 경로가 없다.

## 3. 목표와 제품 원칙

### 3.1 목표

1. 사용자가 전국 지도에서 시장의 위치와 다음 장날을 동시에 파악하게 한다.
2. 사용자가 시장명 또는 지역을 기준으로 방문할 시장을 10초 안에 찾게 한다.
3. 모든 공개 장날 정보에 출처와 기준일 또는 마지막 확인일을 제공한다.
4. 최초 공공데이터를 재현 가능한 절차로 조사·정규화하고, 서비스 운영 중에는 제보와 운영자 검증으로 정확도를 유지한다.
5. 잘못된 장날을 추측해 공개하는 것보다 해당 시장을 검토 대상으로 보류하는 것을 우선한다.

### 3.2 제품 원칙

- 지도 우선: 첫 화면과 핵심 탐색 수단은 목록이 아니라 전국 지도다.
- 날짜가 보이는 핀: 개별 핀에는 시장명과 다음 장날을 함께 표시한다.
- 근거가 보이는 정보: 장날의 출처와 확인 시점을 숨기지 않는다.
- 검증 후 반영: 사용자 제보는 운영자가 확인하기 전 공개 정보에 반영하지 않는다.
- 단순한 상태: 시장 운영 상태는 `운영`, `폐장` 두 값만 사용한다.
- 보수적인 정규화: 해석할 수 없는 원문은 추정하지 않고 검토 대상으로 분류한다.

## 4. 사용자

### 4.1 주요 사용자: 장날 방문자

전통시장과 장날 구경을 좋아하고, 특정 날짜나 지역을 기준으로 방문할 시장을 찾는 사람이다. 시장 이름을 이미 알고 있을 수도 있고, 주변 시장을 탐색하고 싶을 수도 있다. 모바일 환경에서 이동 중 확인하는 상황이 중요하다.

주요 요구:

- 다음 장날을 빠르게 확인하고 싶다.
- 같은 지역의 여러 시장을 지도에서 비교하고 싶다.
- 주소, 연락처, 주차, 길찾기처럼 방문에 필요한 정보를 한곳에서 보고 싶다.
- 정보가 믿을 만한지 출처와 확인일로 판단하고 싶다.

### 4.2 보조 사용자: 정보 제보자

시장 장날, 휴장, 이전 또는 폐장 정보가 잘못된 것을 발견한 방문자나 지역 관계자다. 계정을 만들지 않고 짧게 제보하기를 원한다.

### 4.3 내부 사용자: 운영자

제보와 데이터 이상을 확인하고 시장 정보 및 장날을 수정하는 서비스 관리자다. 변경 근거와 이력을 남기고 잘못된 수정을 되돌릴 수 있어야 한다.

## 5. 핵심 사용 시나리오

### 시나리오 A: 알고 있는 시장의 다음 장날 찾기

1. 사용자가 서비스에 접속한다.
2. 시장명을 검색한다.
3. 지도에서 검색 결과 핀과 다음 장날을 확인한다.
4. 핀을 선택해 상세정보, 남은 일수와 월간 장날을 확인한다.
5. 필요하면 길찾기 링크로 이동한다.

성공 조건: 사용자가 접속 후 10초 안에 다음 장날을 찾는다.

### 시나리오 B: 특정 날짜에 열리는 시장 발견하기

1. 사용자가 `오늘`, `이번 주`, `주말` 또는 직접 날짜를 선택한다.
2. 지도에는 조건에 맞는 시장만 남는다.
3. 사용자가 위치와 다음 장날을 비교해 시장을 선택한다.
4. 상세정보에서 방문 조건과 출처를 확인한다.

성공 조건: 필터 결과와 핀에 표시된 날짜가 일치하고, 지도 이동 후에도 선택 조건이 유지된다.

### 시나리오 C: 주변 시장 탐색하기

1. 사용자가 `내 주변`을 선택하고 위치 사용을 허용한다.
2. 지도는 현재 위치 주변의 시장을 보여준다.
3. 사용자가 여러 핀의 시장명과 다음 장날을 비교한다.
4. 한 시장을 선택해 상세정보를 확인한다.

성공 조건: 위치 권한을 거부해도 지역 검색으로 같은 목적을 달성할 수 있다.

### 시나리오 D: 잘못된 정보 제보하기

1. 사용자가 시장 상세에서 `정보 수정 제보`를 선택한다.
2. 날짜 오류, 휴장, 이전, 폐장 또는 기타 유형과 내용을 입력한다.
3. 선택적으로 근거 URL을 첨부하고 제출한다.
4. 제보는 검토 대기 상태로 저장되고 공개 정보는 즉시 바뀌지 않는다.

성공 조건: 운영자가 제보를 승인 또는 반려하고 처리 근거와 수정 이력을 남긴다.

### 시나리오 E: 운영자가 직접 정보 수정하기

1. 운영자가 제보 또는 자체 확인으로 변경 필요성을 발견한다.
2. 신뢰할 수 있는 출처로 사실을 확인한다.
3. 시장 정보, 장날 또는 운영 상태를 수정하고 근거와 메모를 남긴다.
4. 변경 내용을 검토한 뒤 공개한다.

성공 조건: 변경 전후 값, 작업자, 시각과 근거가 기록되며 이전 값으로 되돌릴 수 있다.

## 6. MVP 범위

### 6.1 포함 범위

- 전국 전통시장 공공데이터의 충분성 조사와 최초 1회 정규화·적재
- 정기시장과 혼합시장의 장날 정보 제공
- 주요 숫자 쌍 장날 표현과 조사로 확정된 추가 규칙의 날짜 계산
- 전국 지도 중심의 홈 화면
- 시장명과 다음 장날을 함께 표시하는 지도 핀
- 핀 밀집 구간의 묶음 표시
- `오늘`, `이번 주`, `주말`, 직접 날짜 선택, `내 주변` 필터
- 시장명 및 지역 검색
- 시장 상세정보와 월간 장날 표시
- 출처, 데이터 기준일과 마지막 확인일 표시
- 외부 지도 또는 내비게이션 길찾기 연결
- 로그인 없는 오류 제보
- 제보 검토와 시장 정보 수정을 위한 최소 운영자 기능
- SSH 기반 관리 CLI
- 변경 이력과 복구 수단
- 모바일·데스크톱 반응형 화면
- 지도 사용 불가 시 지역·날짜 기반 대체 목록

### 6.2 제외 범위

- 일반 사용자 계정, 프로필과 즐겨찾기
- 후기, 별점, 댓글과 사진 업로드
- 여행 코스 자동 추천
- 상인 또는 사용자의 직접 편집 권한
- 커뮤니티 투표나 상호 검증
- 푸시, 문자 또는 이메일 장날 알림
- 광고, 결제와 유료 상품
- 운영 중 공공데이터 자동 동기화 또는 자동 변경 감지
- 네이티브 모바일 앱
- 기술 스택, 지도 제공업체, 호스팅 업체의 사전 확정
- 관리자 웹페이지와 관리자 OAuth 인증

## 7. 기능 요구사항

### 7.1 지도와 탐색

- **FR-01 전국 지도 홈:** 서비스 첫 화면은 전국 범위의 지도를 중심으로 구성해야 한다.
- **FR-02 핀 표시:** 개별 시장 핀은 `시장명 · M/D` 형식으로 시장명과 선택 기준일 이후 가장 가까운 장날을 함께 표시해야 한다.
- **FR-03 핀 가독성:** 개별 핀이 구분되는 확대 수준에서는 시장명을 숨기지 않아야 한다. 핀이 겹치는 축척에서는 묶음 숫자를 사용할 수 있다.
- **FR-04 지도 영역 갱신:** 지도 이동 또는 확대·축소 후 현재 화면 영역과 활성 날짜 조건에 맞는 시장을 표시해야 한다.
- **FR-05 날짜 필터:** 기본 날짜 범위는 `이번 주`이며 `오늘`, `주말`, 직접 날짜 선택을 제공해야 한다.
- **FR-06 내 주변:** 위치 권한이 허용되면 현재 위치 주변 시장을 탐색할 수 있어야 한다. 권한 거부 또는 위치 확인 실패 시 지역 검색을 안내해야 한다.
- **FR-07 검색:** 시장명과 지역명으로 검색할 수 있어야 하며 결과 선택 시 해당 시장 또는 지역으로 지도를 이동해야 한다.
- **FR-08 폐장 시장:** `폐장` 상태의 시장은 기본 탐색 결과와 장날 계산 대상에서 제외해야 한다.

### 7.2 시장 상세정보

- **FR-09 상세 열기:** 사용자가 핀을 선택하면 데스크톱에서는 측면 패널, 모바일에서는 하단 시트로 상세정보를 제공해야 한다.
- **FR-10 필수 상세정보:** 시장명, 위치, 다음 장날, 남은 일수, 해당 월 전체 장날, 시장 유형, 주소, 연락처, 주차 정보, 출처, 데이터 기준일 또는 마지막 확인일을 표시해야 한다. 값이 없으면 없는 사실을 명확히 표시해야 한다.
- **FR-11 길찾기:** 시장 위치를 외부 지도 또는 내비게이션으로 전달하는 길찾기 링크를 제공해야 한다.
- **FR-12 날짜 일관성:** 상세정보의 다음 장날과 월간 장날은 동일한 정규화 규칙과 기준일로 계산해야 한다.

### 7.3 제보

- **FR-13 비로그인 제보:** 일반 사용자 계정 없이 제보할 수 있어야 한다.
- **FR-14 제보 유형:** 날짜 오류, 휴장, 이전, 폐장, 기타를 지원해야 한다.
- **FR-15 제보 내용:** 대상 시장, 제보 유형, 설명을 필수로 받고 근거 URL은 선택적으로 받아야 한다.
- **FR-16 검토 대기:** 제출된 제보는 공개 정보에 자동 반영하지 않고 운영자 검토 대기 상태로 저장해야 한다.
- **FR-17 남용 방지:** 반복 제출 제한과 자동화된 스팸 완화 수단을 적용해야 한다.

### 7.4 운영자 기능

- **FR-18 제보함:** 운영자는 SSH 기반 관리 CLI에서 신규, 검토 중, 승인, 반려 상태로 제보를 조회하고 처리할 수 있어야 한다.
- **FR-19 사실 확인:** 승인 또는 반려 시 확인 근거와 처리 메모를 남겨야 한다.
- **FR-20 수동 수정:** 운영자는 제보가 없어도 확인된 시장 정보와 장날을 직접 수정할 수 있어야 한다.
- **FR-21 운영 상태:** 운영자는 시장 상태를 `운영` 또는 `폐장`으로만 설정할 수 있어야 한다.
- **FR-22 변경 이력:** 변경 전후 값, 변경 시각, 작업자, 근거와 연결된 제보를 기록해야 한다.
- **FR-23 복구:** 운영자는 잘못된 변경을 이전 공개 값으로 되돌릴 수 있어야 한다.

### 7.5 장애와 예외

- **FR-24 지도 대체 화면:** 지도 제공 기능이 실패해도 지역과 날짜 기준의 시장 목록으로 탐색을 계속할 수 있어야 한다.
- **FR-25 미확정 일정:** 해석할 수 없거나 출처가 충돌하는 장날은 계산하거나 공개하지 않고 검토 대상으로 보내야 한다.
- **FR-26 좌표 이상:** 좌표가 없거나 국내 범위를 벗어난 시장은 주소 기반 보완과 운영자 검토를 거치기 전 지도에 공개하지 않아야 한다.
- **FR-27 중복 후보:** 이름과 주소가 유사한 시장은 자동 병합하지 않고 운영자 검토 대상으로 제시해야 한다.

## 8. 비기능 요구사항

- **NFR-01 응답성:** 일반적인 모바일 네트워크에서 첫 화면은 사용자가 진행 상태를 인지할 수 있어야 하며, 지도 조작과 필터 변경은 입력을 막지 않아야 한다. 구체적인 성능 예산은 기술 스택 선정 단계에서 실제 제공업체와 데이터 규모를 기준으로 확정한다.
- **NFR-02 탐색 시간:** 대표 사용성 시험에서 사용자는 시장명 검색 또는 지도 이동을 통해 10초 안에 다음 장날을 찾을 수 있어야 한다.
- **NFR-03 모바일 지원:** 주요 모바일 화면 크기에서 지도 핀 선택, 하단 상세 시트, 날짜 필터와 제보 제출이 가로 스크롤 없이 작동해야 한다.
- **NFR-04 접근성:** 검색, 날짜 선택, 시장 선택과 제보 제출을 키보드로 수행할 수 있어야 한다. 핀의 시장명과 날짜는 화면 읽기 도구가 이해할 수 있는 대체 표현을 제공해야 한다.
- **NFR-05 데이터 정확성:** 계산 가능한 일정은 승인된 기준 사례에서 100% 일치해야 한다. 월말, 윤년, 연말·연초를 포함해야 한다.
- **NFR-06 출처 추적성:** 공개된 모든 장날 값은 원본 또는 운영자 확인 근거와 연결돼야 한다.
- **NFR-07 개인정보 최소화:** 비로그인 제보에 처리 목적상 불필요한 개인정보를 요구하지 않아야 한다. 수집 항목, 보관 기간과 삭제 기준은 공개 전에 확정해야 한다.
- **NFR-08 보안:** MVP 운영자 기능은 개인 서버에 SSH로 접속한 운영자만 관리 CLI로 실행할 수 있어야 하며, 모든 운영자 변경은 작업자 단위로 추적돼야 한다. 관리자 웹페이지와 외부 OAuth 인증은 MVP에서 제공하지 않는다.
- **NFR-09 복구 가능성:** 운영 데이터와 변경 이력을 정기적으로 백업하고, 잘못된 수정 또는 데이터 손상 시 복구 절차를 검증해야 한다.
- **NFR-10 관측 가능성:** 지도 실패, 장날 계산 실패, 제보 제출 실패와 운영자 변경 실패를 운영자가 발견할 수 있어야 한다. 구체적인 도구는 기술 스택 선정 단계에서 결정한다.
- **NFR-11 호환성:** 공개 전 지원 브라우저 범위를 정하고, 해당 범위에서 핵심 시나리오 A~D를 검증해야 한다.

## 9. 데이터 요구사항

### 9.1 최초 데이터 조사 게이트

애플리케이션 구현 전에 `전국전통시장표준데이터` 전체 원본을 조사한다. 다음 결과를 확보해야 한다.

- 전체 행 수와 정기시장·혼합시장 후보 수
- 시장명, 주소, 위도·경도, 시장 유형, 시장개설주기, 전화번호, 주차 정보, 데이터 기준일자의 채움률
- 유효 좌표 비율과 보완 대상 수
- 장날 원문 표현의 전체 분포, 자동 해석 가능 비율과 검토 대상 수
- 중복 후보와 폐장 포함 가능성
- 공개 가능한 시장 수와 전국·권역별 분포
- 원본과 정규화 결과의 표본 수동 검산 결과

조사 판정은 다음 기준을 사용한다.

- 공개 가능 후보 비율 90% 이상: `사용 가능`
- 70% 이상 90% 미만: `보완 후 사용 가능`; 수동 보완량과 운영 가능성을 별도 확인
- 70% 미만: `사용 불가`; 지자체와 관광 데이터 등 추가 원천을 먼저 조사

비율과 관계없이 좌표와 장날이 모두 검증되지 않은 개별 시장은 공개하지 않는다. 조사 결과가 `사용 가능` 또는 현실적인 보완량의 `보완 후 사용 가능`일 때만 서비스 구현 단계로 진행한다.

### 9.2 원본과 정규화 데이터

- 원본 파일은 수정하지 않고 원본 식별 정보, 확보일과 무결성 확인값을 보존해야 한다.
- 원본 필드와 정규화 필드를 함께 보관해 모든 변환 결과를 추적할 수 있어야 한다.
- 운영 중에는 공공데이터를 주기적으로 자동 동기화하지 않는다.
- 최초 적재 이후 공개 데이터 변경은 승인된 사용자 제보 또는 운영자의 확인된 수동 수정으로만 수행한다.

### 9.3 시장 데이터

시장마다 최소한 다음 정보를 관리해야 한다.

- 고유 식별자
- 시장명
- 시장 유형: 상설, 정기, 혼합, 미확인
- 도로명 주소와 지번 주소
- 위도와 경도
- 전화번호
- 주차 정보
- 운영 상태: `운영` 또는 `폐장`

시장 유형의 `미확인`은 데이터 분류값이며 운영 상태가 아니다. 운영 상태에는 다른 값을 추가하지 않는다.

### 9.4 장날 데이터

장날마다 최소한 다음 정보를 관리해야 한다.

- 연결된 시장
- 원본 개설주기 문자열
- 정규화된 규칙 유형과 규칙 값
- 적용 시작일과 종료일(알 수 있는 경우)
- 계산 가능 여부
- 출처와 기준일 또는 마지막 확인일

지원하는 규칙만 자동 확정한다. 예를 들어 숫자 쌍 장날의 해당 일자가 어떤 달에 존재하지 않으면 그 날짜는 생성하지 않는다. `0일` 표기, 요일 기반 규칙, 임시 휴장과 같은 표현의 의미는 데이터 조사 결과와 근거를 바탕으로 별도 확정한다.

### 9.5 출처와 변경 이력

- 시장 또는 장날 정보는 출처 유형, URL 또는 식별자, 출처 기준일, 마지막 확인일과 원본 값을 가질 수 있어야 한다.
- 운영자 수정은 확인 근거를 필수로 가져야 한다.
- 변경 이력은 변경 전후 값, 작업자, 시각, 근거와 관련 제보를 보존해야 한다.
- 공개 화면에는 사용자가 신뢰도를 판단할 수 있는 출처와 확인 시점을 표시해야 한다.

### 9.6 제보 데이터

- 대상 시장
- 제보 유형
- 제보 내용
- 선택적 근거 URL
- 처리 상태와 처리 메모
- 생성 시각과 처리 시각
- 승인된 경우 연결된 변경 이력

제보 처리 상태는 운영 흐름을 위한 값이며 시장 운영 상태와 분리한다.

## 10. 운영 흐름

### 10.1 최초 공개 전

```text
공공데이터 원본 확보
  → 충분성·품질 조사
  → 장날 규칙 분류와 수동 검산
  → 공개 가능 / 보완 후 가능 / 사용 불가 판정
  → 필요한 수동 보완
  → 최초 1회 정규화·적재
  → 공개 데이터와 출처 검수
  → MVP 공개 승인
```

### 10.2 공개 후 사용자 제보 처리

```text
사용자 제보
  → 자동 남용 점검
  → 운영자 검토 대기
  → 출처로 사실 확인
  → 승인 또는 반려
  → 승인 시 수동 수정
  → 변경 이력 기록
  → 공개 정보 갱신
```

### 10.3 운영자 직접 수정

```text
운영자가 변경 발견
  → 출처 확인
  → 수정안과 근거 기록
  → 공개 정보 갱신
  → 변경 이력 보관
```

### 10.4 운영 원칙

- 미확인 제보는 공개 정보에 자동 반영하지 않는다.
- 공공데이터의 운영 중 자동 갱신은 하지 않는다.
- 장날 충돌 시 더 최신이라는 이유만으로 자동 선택하지 않고 출처 신뢰도와 실제 시장 정보를 확인한다.
- 폐장 처리는 장날 표시와 기본 탐색 노출에 즉시 영향을 주므로 근거를 확인하고 이력을 남긴다.
- 운영자가 처리할 수 있는 제보량을 넘으면 접수 순서, 영향 범위와 근거 품질을 기준으로 우선순위를 정한다. 구체적인 처리 목표시간은 공개 전 확정한다.

## 11. 성공 지표

### 11.1 공개 준비 지표

- 데이터 조사 보고서가 9.1의 모든 항목을 실제 수치로 제공한다.
- 조사 판정이 `사용 가능` 또는 운영 가능한 보완량의 `보완 후 사용 가능`이다.
- 공개 대상 시장의 100%가 유효 좌표, 계산 가능한 장날, 출처를 가진다.
- 지원 규칙의 기준 사례와 월말·윤년·연말 경계 사례가 100% 정확하다.
- 원본과 정규화 결과를 유형별로 수동 검산하고 불일치가 해결됐다.

### 11.2 사용자 가치 지표

- 대표 사용성 시험 참가자의 80% 이상이 도움 없이 10초 안에 지정 시장의 다음 장날을 찾는다.
- 대표 사용성 시험 참가자의 80% 이상이 특정 날짜에 열리는 시장을 찾아 상세정보까지 연다.
- 핵심 흐름 `지도 탐색 → 핀 선택 → 다음 장날 확인`의 완료율이 90% 이상이다.
- 시장 상세를 연 사용자 중 출처 또는 길찾기 등 방문 판단 정보를 확인하는 비율을 측정한다. 목표값은 베타 기준선 수집 후 확정한다.

### 11.3 데이터·운영 지표

- 공개 중인 장날 정보의 출처 연결률은 100%다.
- 승인된 수정의 변경 이력 기록률은 100%다.
- 검증된 오정보가 공개 상태로 남아 있는 시간을 측정하고, 처리 목표시간은 베타 운영량을 본 뒤 확정한다.
- 제보 접수 수, 유효 제보율, 승인·반려 비율과 처리 소요시간을 주 단위로 확인한다.
- 지도, 검색, 상세정보, 제보 제출의 실패율을 측정하며 허용 목표는 기술 스택과 관측 기준을 정한 뒤 확정한다.

## 12. 출시 승인 기준

다음 조건을 모두 만족해야 MVP를 공개할 수 있다.

1. 데이터 조사 게이트를 통과했다.
2. 전국 공개 대상이 권역별로 확인됐고 누락 범위가 문서화됐다.
3. 모든 공개 시장 핀에 시장명과 다음 장날이 함께 표시된다.
4. 시장 상세정보에 장날, 출처와 확인 시점이 표시된다.
5. 미확정 장날, 잘못된 좌표와 중복 후보가 자동 공개되지 않는다.
6. 모바일과 데스크톱에서 핵심 시나리오 A~D가 검증됐다.
7. 제보의 접수, 검토, 승인·반려, 수정과 이력 기록 흐름이 검증됐다.
8. 지도 장애 시 대체 목록에서 핵심 탐색을 계속할 수 있다.
9. 운영 데이터 백업과 변경 복구 절차를 검증했다.
10. 개인정보 처리, 지도 이용약관과 공공데이터 이용조건을 확인했다.

| 지도 제공 기능 장애 또는 정책 변경 | 핵심 탐색 중단 또는 비용 증가 | 지역·날짜 대체 목록, 제공업체 비교 시 비용·약관·장애 대응 검토 |

| 출처의 이용조건 또는 개인정보 처리 미비 | 공개 중단 또는 법적 위험 | 공개 전 이용조건, 표시 의무, 개인정보 수집·보관 정책 검토 |

## 14. 열린 결정

다음 항목은 PRD 승인 후 또는 데이터 조사 결과를 바탕으로 결정한다.

### 14.1 제품·운영 결정

- 공공데이터가 부족할 때 지자체·관광 데이터로 보완할 범위와 우선순위
- 요일 기반, `0일` 표기, 임시 휴장 등 추가 장날 규칙의 지원 범위
- 제보에 증빙 사진 업로드를 포함할지 여부
- 사용자에게 제보 처리 결과를 알릴지, 알린다면 연락처를 어떤 방식으로 받을지
- 운영자의 제보 처리 목표시간과 일일 처리 가능량
- 폐장 시장을 검색으로 별도 조회할 수 있게 할지 여부
- 베타 대상 사용자 수, 기간과 정량 지표의 최종 목표값
- 지원 브라우저와 접근성 검증 범위

### 14.2 기술 결정 — 별도 결정 문서

아래 항목은 대안과 장단점, 비용, 운영 영향을 비교해 사용자에게 질문하고 사용자가 최종 결정한다. 추천안을 제시할 수는 있지만 사용자 확인 없이 자동으로 선택하거나 구현하지 않는다.

- 프론트엔드 구조와 프레임워크
- API 방식과 서버 구조
- 데이터베이스와 백업·복구 방식
- 국내 지도 제공업체와 외부 길찾기 연동 방식
- 관리자 인증과 권한 관리 방식
- 서비스를 올릴 호스팅·배포 대상과 관측 방식

비교 기준에는 초기·월간 비용, 국내 지도 품질, 예상 사용량, 사용량 제한, 이용약관, 접근성, 장애 대응, 개발·운영 난이도, 데이터 이전 가능성을 포함한다.

선택 결과는 `기술스택-결정.md`에 기록한다.

## 15. 승인 게이트와 다음 단계

이 문서의 승인 전에는 다음 작업을 시작하지 않는다.

- 기술 스택 확정
- 애플리케이션 코드 작성
- 패키지 설치 또는 프로젝트 스캐폴드 생성
- 데이터베이스 생성 또는 스키마 적용
- 지도 제공업체 연동
- 관리자 인증 또는 호스팅 구성

PRD 승인 후에도 곧바로 애플리케이션을 구현하지 않는다. 다음 별도 단계에서 프론트엔드, API, 데이터베이스, 국내 지도 제공업체, 관리자 인증과 호스팅·배포 대상의 대안을 비교해 사용자에게 질문한다. 기술 스택과 서비스를 올릴 곳은 사용자가 명시적으로 선택한 뒤에만 확정한다. 이후 데이터 조사 게이트를 통과한 경우에만 구현 계획을 작성한다.
