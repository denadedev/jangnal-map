# 시장별 온누리상품권 가맹점 수 및 검색 유입 설계

## 목표

전통시장 상세에서 시장별 온누리상품권 가맹점 규모를 신뢰할 수 있는 기준일과 함께 제공한다. 동시에 기존 시장 상세 페이지와 온누리상품권 허브 페이지가 다음 두 종류의 검색 의도를 받을 수 있게 한다.

- `○○시장 온누리상품권`, `○○시장 온누리상품권 사용처`처럼 특정 시장을 찾는 검색
- `온누리상품권 사용처`, `온누리상품권 가맹점`처럼 전국 단위 정보를 찾는 검색

## 성공 기준

- 공식 전국 가맹점 원본에서 시장별 중복 제거 전체 가맹점 수, 디지털 가맹점 수, 지류 가맹점 수를 계산한다.
- 신뢰도 기준을 통과한 시장만 가맹점 수를 노출한다.
- 지도 상세 패널과 정적 시장 상세 페이지가 동일한 수치, 기준일, 출처를 표시한다.
- `/onnuri` 페이지가 온누리상품권 설명, 시장 검색, 주요 시장 진입점을 제공한다.
- 시장 상세 메타데이터가 온누리상품권 관련 검색 의도를 자연스럽게 포함하되 수치가 없는 시장에는 확인되지 않은 표현을 생성하지 않는다.

## 범위

### 포함

- 공식 온누리상품권 가맹점 CSV 수집 및 정규화
- 기존 전국 전통시장 데이터와의 시장 단위 매칭
- 전체·디지털·지류 가맹점 수 집계
- 매칭 예외를 위한 명시적 수동 매핑 파일
- 공개 시장 JSON 스키마 확장
- 지도 상세 패널과 정적 시장 상세 페이지 노출
- `/onnuri` 온누리상품권 허브 및 시장 검색
- 메타데이터, 내부 링크, 사이트맵 보강
- 데이터 처리, 화면, SEO 관련 자동 테스트

### 제외

- 개별 가맹점 목록과 가맹점 상세 페이지
- 외부 API의 요청 시점 실시간 호출
- 사용자 위치 기반 주변 가맹점 탐색
- 결제·구매·충전 기능
- 자동 생성 지역별 온누리상품권 랜딩 페이지

## 데이터 원천과 갱신 방식

소상공인시장진흥공단이 공공데이터포털에서 제공하는 `전국 온누리상품권 가맹점 현황`을 기준 데이터로 사용한다. 원본에는 가맹점명, 소속 시장명, 소재지와 디지털·지류 등 취급 유형이 포함된다.

서비스 요청 중에는 외부 API를 호출하지 않는다. 데이터 갱신 시 원본 CSV를 내려받아 로컬 데이터 생성 파이프라인에 입력하고, 기존 `markets.json` 생성 단계에서 집계 결과를 병합한다. 이렇게 하면 정적 배포 구조를 유지하고 외부 장애나 호출 제한이 사용자 요청에 영향을 주지 않는다.

원본 데이터의 기준일과 공식 출처 URL을 집계 결과에 함께 보존한다. 원본이 연간 갱신되므로 화면에는 수치와 함께 기준일을 항상 표시하고, 실제 가맹 상태가 변경될 수 있다는 안내를 제공한다.

## 정규화와 매칭

### 가맹점 중복 제거

전체 가맹점 수는 디지털 수와 지류 수를 더한 값이 아니다. 동일 점포가 여러 결제 유형을 지원할 수 있으므로 다음 정규화 키를 이용해 중복을 제거한다.

- 정규화한 소속 시장명
- 정규화한 가맹점명
- 정규화한 주소

주소가 비어 있는 행은 시장명과 가맹점명으로 묶되, 같은 키가 반복되면 원본 행 번호를 붙여 별도 점포로 유지한다. 디지털·지류 수는 각 유형을 지원하는 중복 제거 점포 수로 계산한다. 원본의 결제 유형 열 이름이나 값이 연도별로 달라질 수 있으므로 지원 값의 허용 목록을 버전별로 명시하고, 알려지지 않은 값은 임의로 디지털 또는 지류로 분류하지 않는다.

### 시장 매칭

자동 매칭은 다음 조건을 모두 활용한다.

1. 괄호, 공백, 법정 접미 표현을 정리한 시장명
2. 시·도와 시·군·구가 일치하는 주소
3. 이름이 유사할 때 주소 또는 지역이 뒷받침되는지 여부

정확히 하나의 시장으로 결정되는 경우만 자동 확정한다. 여러 후보가 있거나 지역 정보가 충돌하면 공개 JSON에 합치지 않고 미매칭 보고서에 남긴다. 확인된 예외는 원본 이름·지역과 내부 시장 ID를 연결하는 수동 매핑 파일에 기록한다. 수동 매핑은 이유를 주석 또는 구조화된 메모로 남겨 검토 가능하게 한다.

### 품질 보고서

생성 명령은 다음 통계를 출력한다.

- 전체 원본 가맹점 수와 중복 제거 수
- 자동 매칭, 수동 매칭, 미매칭 시장 수
- 현재 서비스 시장 중 온누리 수치가 연결된 시장 비율
- 이름 또는 지역 충돌 목록

미매칭은 `0곳`으로 변환하지 않는다. 데이터 부재와 실제 0곳을 구분하기 위해 미매칭 시장의 집계 필드는 `null`로 유지한다.

## 공개 데이터 모델

`PublicMarket`에 다음 선택 필드를 추가한다.

```ts
interface OnnuriMerchantSummary {
  totalCount: number;
  digitalCount: number;
  paperCount: number;
  referenceDate: string;
  source: {
    name: string;
    url: string;
  };
}

interface PublicMarket {
  // 기존 필드
  onnuri: OnnuriMerchantSummary | null;
}
```

`totalCount`는 결제 유형 전체의 중복 제거 점포 수다. `digitalCount`와 `paperCount`는 서로 중복될 수 있으므로 합계가 전체 수와 같다는 전제를 두지 않는다.

## 화면 설계

### 지도 상세 패널

`방문 정보` 다음에 `온누리상품권` 섹션을 둔다. 집계가 있으면 다음 정보를 표시한다.

- `가맹점 총 83곳`
- `디지털 71곳 · 지류 65곳`
- `2025.07.31 기준`
- 공식 가맹점 찾기 링크
- `점포별 취급 여부는 변경될 수 있으니 방문 전 공식 가맹점 찾기에서 확인하세요.` 안내

집계가 없으면 숫자를 만들지 않고 `가맹점 수 확인 필요`와 공식 조회 링크만 제공한다.

### 정적 시장 상세 페이지

지도 상세 패널과 같은 내용을 별도 섹션으로 제공한다. 서버 렌더링된 텍스트에 시장명, 온누리상품권, 전체·디지털·지류 수가 포함되어 검색엔진과 보조 기술이 동일한 정보를 읽을 수 있게 한다.

### `/onnuri` 허브

허브는 다음 순서로 구성한다.

1. 온누리상품권 사용처를 시장별로 찾는다는 페이지 목적
2. 시장명 또는 지역 검색
3. 검색 결과 카드의 시장명, 지역, 전체·디지털·지류 가맹점 수
4. 가맹점 수가 확인된 주요 시장 진입점
5. 디지털·지류의 차이와 데이터 기준일에 대한 짧은 안내
6. 공식 가맹점 찾기 링크와 변경 가능성 고지

검색 결과는 클라이언트에서 기존 정적 시장 데이터를 필터링한다. 별도 검색 API나 데이터베이스를 추가하지 않는다. 각 결과는 기존 `/markets/[slug]` 페이지로 연결한다.

## 검색 최적화

### 시장 상세 페이지

가맹점 수가 있는 시장은 제목과 설명에 `시장명`, `온누리상품권`, `가맹점 수`를 포함한다. 정확한 숫자는 기준 데이터가 있는 경우에만 사용한다. 기존 장날 키워드를 제거하지 않고 두 검색 의도를 함께 담는다.

예시:

- 제목: `○○시장 장날·온누리상품권 가맹점 83곳`
- 설명: `○○시 ○○시장의 장날과 온누리상품권 가맹점 83곳, 디지털·지류 사용 가능 점포 수, 주소와 주차 정보를 확인하세요.`

집계가 없는 시장은 기존 장날 중심 제목과 설명을 유지한다.

### 허브 페이지

`/onnuri`는 자체 canonical URL과 `온누리상품권 사용처`, `온누리상품권 가맹점` 중심의 고유 제목·설명을 가진다. 허브에서 수치가 있는 시장 상세 페이지로 내부 링크하고, 홈과 시장 상세에서도 허브로 연결한다. 사이트맵에 허브를 포함한다.

얇은 콘텐츠가 대량 생성되는 것을 피하기 위해 이번 범위에서는 지역별 랜딩 페이지를 만들지 않는다. 검색 유입과 사용자 행동 데이터를 확인한 뒤 별도 설계한다.

## 오류와 예외 처리

- 원본 필수 열이 없으면 생성 명령을 실패시킨다.
- 음수, 비정상 숫자, 알 수 없는 결제 유형은 오류 보고서에 기록하고 집계에서 제외한다.
- 기준일이 없으면 해당 원본을 공개 데이터로 병합하지 않는다.
- 한 가맹점이 여러 시장에 소속된 것으로 보이면 자동 통합하지 않는다.
- 공식 링크는 새 창으로 열고 외부 링크 속성을 지정한다.
- 데이터 생성 실패는 기존 공개 JSON을 부분적으로 덮어쓰지 않는다.

## 테스트

### 데이터 처리

- 시장명·주소 정규화
- 동일 점포의 결제 유형 중복 제거
- 전체·디지털·지류 수의 독립 집계
- 동명 시장의 지역 구분
- 수동 매핑 적용
- 충돌·미매칭 보고
- 기준일 또는 필수 열 누락 시 실패
- 기존 전통시장 JSON 병합

### 화면

- 집계가 있는 시장의 세 수치와 기준일 노출
- 집계가 없는 시장의 `확인 필요` 상태
- 공식 링크와 안내 문구
- 지도 상세와 정적 상세의 표현 일치
- `/onnuri` 검색과 상세 페이지 링크

### SEO

- 집계가 있는 시장만 온누리 수치를 메타데이터에 포함
- 집계가 없는 시장은 기존 메타데이터 유지
- `/onnuri` canonical과 사이트맵 등록
- 정적 빌드 성공

## 운영 절차

1. 공식 최신 CSV와 기준일을 확인한다.
2. 데이터 생성 명령을 실행한다.
3. 품질 보고서의 충돌과 미매칭을 검토한다.
4. 필요한 예외만 수동 매핑에 추가한다.
5. 테스트와 정적 빌드를 실행한다.
6. 생성된 공개 JSON과 매칭률 변화를 함께 리뷰한다.

정기 갱신 자동화는 원본의 실제 갱신 주기가 안정적으로 확인된 뒤 별도 작업으로 둔다. 이번 구현에서는 재현 가능한 수동 갱신 명령과 검증 보고서를 제공한다.
