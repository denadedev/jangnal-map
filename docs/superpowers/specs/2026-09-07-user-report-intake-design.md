# 사용자 제보 이메일 접수 설계

- 상태: APPROVED
- 작성일: 2026-09-07
- 적용 단계: 정적 MVP

## 문제

오늘장날에는 잘못된 시장 정보와 서비스 이용 불편을 사용자가 알려줄 수 있는 일관된 경로가 없다. `mailto:` 링크는 메일 앱 설정과 제목·시장명 작성을 사용자에게 맡겨 모바일과 디지털 사용이 익숙하지 않은 사용자에게 진입장벽이 된다.

운영자는 여러 채널을 확인하지 않고 하나의 이메일에서 제보를 받아야 한다. 사용자는 계정이나 메일 앱 없이 오늘장날 화면 안에서 짧게 제출할 수 있어야 한다.

## 목표

- 로그인과 메일 앱 없이 1분 안에 제보를 제출한다.
- 시장 정보 수정과 서비스 불편 신고를 같은 운영 이메일로 모은다.
- 시장 상세에서 들어온 제보에는 검증된 시장 ID와 이름을 자동으로 연결한다.
- 제보를 별도 데이터베이스에 저장하지 않는다.
- 제보가 공개 데이터에 자동 반영되지 않도록 한다.

## 범위 밖

- 데이터베이스 기반 제보함과 관리자 화면
- 사용자 계정과 처리 상태 조회
- 사진과 파일 업로드
- 자동 답변 및 공개 데이터 자동 수정
- 전화, 문자와 메신저 상담 채널

## 결정

오늘장날의 전용 `/report` 화면에서 입력받고, 같은 출처의 `/api/report`가 Nodemailer와 Gmail SMTP를 통해 전용 운영 이메일로 발송한다.

Nodemailer는 메일 서비스가 아니라 SMTP 클라이언트다. 발송에는 전용 Google 계정, 2단계 인증과 앱 비밀번호를 사용한다. SMTP 자격증명은 Vercel 서버 환경 변수에만 두고 브라우저와 저장소에 노출하지 않는다.

## 진입점

### 시장 정보 수정 제보

- 지도 시장 상세의 정보 출처 아래에 `정보가 다른가요? 수정 제보` 링크를 둔다.
- 시장별 검색 유입 페이지의 방문 정보 버튼 영역에도 같은 링크를 둔다.
- 링크는 `/report?kind=market&market={시장 ID}`로 이동한다.
- 서버가 공개 시장 데이터에서 ID를 다시 조회하고 시장명을 결정한다.

### 서비스 불편 신고

- 지도 상단 헤더와 시장별 검색 유입 페이지 상단에 `불편 신고` 링크를 둔다.
- 링크는 `/report?kind=service`로 이동한다.

## 입력 항목

### 필수

- 제보 범위: 진입 경로에 따라 `시장 정보` 또는 `서비스 불편`으로 고정한다.
- 세부 유형
  - 시장 정보: `장날·운영일`, `휴장·폐장`, `위치·주소`, `전화·주차`, `기타`
  - 서비스 불편: `화면·버튼 오류`, `정보를 찾기 어려움`, `지도·위치 문제`, `기타`
- 내용: 빈 문자열은 거부하고 최대 1,000자로 제한한다.

### 선택

- 대상 시장: 시장 정보 제보일 때 URL의 ID를 서버가 검증한다.
- 근거 URL: `http` 또는 `https`만 허용한다.
- 답변받을 연락처: 전화번호 또는 이메일, 최대 100자
- 개인정보 수집 동의: 연락처를 입력한 경우에만 필수다.

## 제출 흐름

1. `/report`가 쿼리의 `kind`와 `market`을 해석한다.
2. 시장 ID가 유효하면 ID와 이름만 클라이언트 폼에 전달한다.
3. 클라이언트가 입력을 검증하고 `/api/report`에 JSON을 보낸다.
4. API가 동일 출처, 본문 크기, honeypot, 유형, URL, 연락처 동의와 시장 ID를 다시 검증한다.
5. API는 서버 환경 변수로 Gmail SMTP에 연결해 일반 텍스트 이메일을 보낸다.
6. 성공하면 접수 완료 화면을, 실패하면 입력값을 유지한 재시도 안내를 보여준다.

## 이메일

- 발신: `오늘 장날 <SMTP_USER>`
- 수신: `REPORT_TO_EMAIL`, 없으면 `SMTP_USER`
- 제목
  - 시장: `[오늘장날] 시장 정보 수정 제보 - {시장명}`
  - 서비스: `[오늘장날] 서비스 불편 신고`
- 본문: 제보 범위, 검증된 시장명·ID, 유형, 내용, 근거 URL, 선택 연락처, 제출 화면
- HTML을 사용하지 않고 일반 텍스트로만 구성한다.
- 파일과 외부 URL을 Nodemailer가 직접 읽지 못하도록 차단한다.

## 개인정보

- 연락처는 답변이 필요한 사용자만 선택적으로 입력한다.
- 연락처 입력란에 수집 목적과 처리 완료 후 90일 이내 삭제 정책을 표시한다.
- 연락처를 입력하면 별도 동의 체크를 요구한다.
- 제보 이메일은 처리 완료 후 90일 이내 삭제한다.
- 공개 데이터와 변경 근거에는 연락처를 복사하지 않는다.
- 삭제 요청은 공개된 `REPORT_TO_EMAIL`로 받는다.

## 보안과 오용 방지

- `SMTP_PASS`는 서버 환경 변수에서만 읽고 응답·로그·클라이언트 번들에 포함하지 않는다.
- Vercel 함수 실행 지역은 서울 `icn1`로 지정한다.
- Production 공개 전에 Vercel Firewall에서 `POST /api/report`에 IP당 10분 5건의 고정 구간 요청 제한을 게시하고 초과 요청은 429로 응답한다.
- 일반 로그인 비밀번호가 아니라 Google 앱 비밀번호를 사용한다.
- 요청 본문은 10,000자보다 크면 거부한다.
- 다른 Origin에서 들어온 브라우저 요청은 거부한다.
- honeypot이 채워진 제출은 메일을 보내지 않고 성공처럼 종료한다.
- 모든 사용자 입력은 일반 텍스트 본문에만 넣고 메일 수신자와 발신자를 바꾸지 못하게 한다.
- SMTP 연결, greeting과 DNS timeout은 5초, socket timeout은 10초로 제한한다. 순차 최악 합계 25초보다 충분히 긴 40초를 함수 최대 실행시간으로 설정한다.
- 요청 제한을 우회한 스팸이 반복되면 CAPTCHA를 추가한다.

동일 출처 검사와 honeypot은 직접 HTTP 요청을 완전히 막지 못한다. Vercel Firewall 요청 제한 게시를 Production 공개의 필수 조건으로 둔다.

## 오류와 예외

- SMTP 계정이나 앱 비밀번호가 없으면 제출 버튼을 비활성화한다.
- 존재하지 않는 시장 ID는 메일을 보내지 않고 시장 선택 안내를 보여준다.
- 클라이언트와 서버에서 유형, 필수 내용, URL과 연락처 동의를 모두 검증한다.
- SMTP 연결 또는 발송 실패는 502로 응답하고 입력값을 유지한다.
- API가 429를 반환하면 운영 이메일을 대체 수단으로 제공한다.
- 제출 중 버튼을 비활성화하고 화면 읽기 도구에 상태를 알린다.

## 운영 절차

1. 운영자는 메일 라벨 `신규`, `확인 중`, `완료`, `반려`로 상태를 관리한다.
2. 장날, 폐장, 이전 제보는 시장 공식 채널, 지자체 또는 신뢰 가능한 공개 출처로 확인한다.
3. 확인 근거와 판단 메모를 데이터 보정 기록에 남긴다.
4. 공개 JSON을 다시 생성하고 전체 테스트와 빌드를 실행한다.
5. 사용자의 배포 승인을 받은 뒤 Vercel에 반영한다.
6. 연락처가 있으면 결과를 회신하고 완료 처리한다.

## 자체 시스템 전환 기준

- 유효 제보가 주 5건을 4주 연속 초과한다.
- 미처리 제보가 20건 이상 누적된다.
- 두 번째 운영자가 추가된다.
- 메일 분류만으로 제보 처리 이력을 추적하기 어렵다.

## 성공 기준

- 시장 상세와 시장별 검색 페이지에서 검증된 시장 제보 화면으로 이동한다.
- 지도 헤더와 시장별 검색 페이지에서 서비스 불편 신고 화면으로 이동한다.
- 로그인, 메일 앱과 외부 폼 화면 없이 제출한다.
- 시장명, 유형, 내용, 근거 URL과 선택 연락처가 운영자 이메일 한 곳에 도착한다.
- SMTP 자격증명이 클라이언트와 저장소에 노출되지 않는다.
- 성공, 실패, 설정 누락과 잘못된 시장 상태가 명확히 표시된다.
- 키보드만으로 입력과 제출을 수행한다.
- 375px 화면에서 가로 스크롤이 없다.
- 전체 테스트, 타입 검사와 프로덕션 빌드가 통과한다.
